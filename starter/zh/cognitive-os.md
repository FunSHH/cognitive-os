# 认知引擎 · Cognitive OS

> 一个用 LLM 搭建**判断引擎**的范式。
>
> 这是一份"想法文档"（idea file）—— 把它整份复制粘贴给你的 LLM Agent（Claude Code / Cowork / Codex / Cursor 等任何能读写文件的 agent），让它和你一起把这套范式落地成适合你领域的具体实现。
>
> 它与 [Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 同源，但指向更高一层的问题 —— **LLM Wiki 帮你积累知识；认知引擎帮你积累判断。**

---

## 核心思想

LLM Wiki 解决了 **Knowledge 层**（DIKW 四层结构：Data → Information → Knowledge → Wisdom）的痛点 —— 把"维护知识"的负担外包给 LLM，让知识真的能积累，而不是在每次提问时被重新合成。

但对于任何**需要做决策**的知识工作者 —— 投资人、研究者、产品决策者、政策分析师、创业者 —— Knowledge 不是瓶颈，**Judgment（判断）才是**。同一组事实，在不同人手里产出的是完全不同的决策。差别在哪？**在这个人的判断是如何形成、验证、被证伪、被升级的结构**。

LLM 让知识每年变得更便宜 —— 这件事已经是事实。**判断才是稀缺品**：带有置信度（confidence）、带有证伪条件（falsifier）、带有证据链（evidence trail）、带有协议化触发条件（protocol）的观点。

LLM 天然不会"建判断"—— 它倾向于把判断**抹平**。问它一个问题，它给你一个答案，但没有置信度、没有证伪条件、没有"什么会让我改变想法"的承诺。

> **LLM Wiki 告诉你"资料怎么说"。**
> **认知引擎告诉你"*你*怎么看、有多确信、什么会让你改观"。**

核心想法是：**建一个判断的 wiki，不只是知识的 wiki。** 每个判断都是一份带结构化元数据的 markdown 文件 —— 领域（domain）、层级（layer）、置信度（confidence）、证据列表（evidence）、证伪条件（falsifier）、演化阶段（evolution-stage）、关联方法论（methodology）。LLM 维护这个判断图谱，方式和 LLM Wiki 维护知识图谱一样 —— 只不过它跟踪的是**你的观点**和**让你改变观点的条件**，不只是事实。

这是关键差异：**这个 wiki 是关于"你怎么想"的持续累积的工程对象。** 不是你读过什么，是你结论是什么。不是世界上的普遍真理，而是你<strong>现在押的注</strong>，以何种置信度，对照何种证伪条件。

维护工作几乎不需要你做 —— LLM 写、LLM 维护。你只做这件事最不能外包的部分：**形成观点、签下证据、签下协议**。LLM 做的是：交叉引用、证伪监测、证据追加、状态推进、反馈反向路由。

## 架构

四层（LLM Wiki 是三层）：

**Raw 原始层** —— 你精心管理的原始资料库：文章、论文、市场数据、播客笔记、你自己的草稿。不可变，LLM 只读不改。

**Knowledge 知识层** —— LLM 维护的 wiki 页面：实体、概念、理论、书摘、对比、综合。**这就是 LLM Wiki 的层** —— Karpathy 那篇所讲的层。它说的是"世界上什么是真的"，不依赖谁读它。

**Cognition 认知层 ★** —— 这是新加的层。LLM 维护的 markdown 文件，每个节点代表**你的判断**，包含：
- `domain` —— 哪个领域（投资 / 研究 / 产品 / 政策 / …）
- `layer` —— 哪种类型（世界观 / 理论 / 框架 / 论述 / 观察）
- `confidence` —— 🔴（初判）/ 🟡（验证中）/ 🟢（稳定）
- `evidence` —— 带时间戳的列表，每条指向 Knowledge 层的某个页面
- `falsifiers` —— 会让这个判断失效的具体条件，命名为 F1 / F2 / F3
- `evolution-stage` —— 这个判断关注的现象当前处在生命周期的哪一段（萌芽 / 加速 / 制度化 / 拥挤 / 退潮）
- `methodology` —— 链接到对应的方法论文件，当判断失败时哪个方法论应该被升级

**Methodology 方法论层** —— 程序性知识：你在这个领域怎么做决策、签下了什么协议、套用什么框架。**这些是"判断节点会调用的程序"。** 当反馈表明某条协议失效了，方法论被更新，更新会**反向传播证据**到所有引用它的判断节点。

四层一起构成**一个能反思自己的图谱**：
- Raw 流向 Knowledge
- Knowledge 喂养 Cognition（每个判断引用 Knowledge 页面）
- Cognition 触发 Methodology（判断调用协议）
- Methodology 被反馈更新后，反向传播证据回 Cognition

## 五个核心操作

LLM Wiki 有三个操作（Ingest / Query / Lint）。认知引擎加两个聚焦于"判断"的操作：

**1. 摄入 Ingest** —— 同 LLM Wiki：新资料进来，LLM 写 Knowledge 摘要、更新实体页、标记矛盾。**附加**：如果资料触动某个已存在的判断节点，LLM 自动在该节点的 `evidence:` 列表末尾追加一条带时间戳的一句话摘要，重新评估对应 falsifier 的状态，**建议**置信度更新（不会未经确认就改）。

**2. 查询 Query** —— 同 LLM Wiki：你提问，LLM 找相关页面综合回答。**附加**：当你问"我对 X 怎么看"时，LLM 必须读 Cognition Wiki —— **不能凭空生成新观点**。它必须把你过去写过的判断（含 confidence + falsifier 状态）作为回答的核心。

**3. 巡检 Lint** —— 周期性健康检查。LLM Wiki 已有部分：
- Knowledge 层：孤立页、过期声明、矛盾、缺失实体。

**附加 Cognition 层巡检**：
- 多个月没被新证据触动的判断节点（可能已过期但没人注意）
- 接近触发的 falsifier 但你还没复核
- 互相矛盾的两个判断
- 缺失 methodology 字段的 Domain / Meta 层节点
- 证据链断裂（指向已删除的 Knowledge 页面）

**4. 证伪扫描 Falsifier Sweep ★** —— 每日心跳。扫描所有 active 判断节点，检查世界是否在向某个 falsifier 的触发条件靠近。LLM 报告："今天判断 A 的 F2 又增加了 3 条支持证据；判断 B 的 F4 首次量化达标，请你复核；判断 C 接近 falsifier 触发，建议你重新看一眼"。**这就是让判断图谱保持活性的机制**，没有它，判断会"被遗忘式失效"。

**5. 反馈反向更新 Feedback Reverse-Update ★** —— 当你基于某个判断采取了行动，得到了结果（对 / 错 / 部分对），结果变成一个反馈文件。LLM 摄入反馈，更新方法论文件，**然后反向传播**：扫描所有引用了被更新方法论的 Cognition 节点，每个节点的 evidence 列表追加一条 "[date] 方法论更新：<一句话摘要>"。**这关闭了循环**：判断 → 行动 → 结果 → 方法论升级 → 所有相关判断同步学到这一课。

## Schema · 最关键的一个文件

`SCHEMA.md` 之于认知引擎，相当于 `CLAUDE.md` 之于 LLM Wiki —— 它是配置文件，让 LLM 从"通用聊天机器人"变成"有纪律的判断引擎维护者"。

Schema 应该定义：
- **判断节点的 frontmatter 字段**（哪些必填、哪些可选）
- **置信度语义** —— 🔴 / 🟡 / 🟢 各对应什么
- **Falsifier 命名约定** —— 例如 F1 / F2，每个一句话陈述
- **演化阶段分类** —— 你的领域用什么阶段词（默认可以用 萌芽 E / 加速 A / 制度化 S- / 拥挤 S+ / 退潮 B-）
- **methodology 反向更新规则** —— 当某个方法论被更新时，哪些判断自动追加证据
- **交叉引用约定** —— evidence 怎么指向 Knowledge 页面；methodology 字段怎么指向 Methodology 文件
- **日 / 周维护协议** —— LLM 不需要问就该做的事
- **摄入路由** —— 新资料进来后，应该去哪一层（只是 Knowledge？触发一个判断？开一个新主题？）

**Schema 与你的 LLM 协同演化**。不要试图一开始就写得完美。每次发现"LLM 做了 X 但应该做 Y"，就把规则写进 Schema，下次它就照做了。几周后，Schema 自然反映你真实的工作流。

## 为什么这件事重要

**从"知识工作者"到"判断工作者"**。区分一个高级分析师和初级分析师的不是记忆里的事实数量 —— 是判断的质量、校准度、和更新纪律。投资、研究、产品、决策者都一样。**判断是资产，知识只是输入**。

**LLM 正在把 Knowledge 商品化**。十年后，你脑子里背的所有事实，任何人都能一个 prompt 拿到。你的竞争优势不能再坐在"知识密度"上。它必须坐在**判断质量**上 —— 而判断质量只有在一个**强制你高频、结构化地形成与更新判断**的系统里，才会复利。

**瓶颈是 bookkeeping**。形成第一天的好判断不难 —— 读完一篇文章你就有意见。**让一个判断在 90 天里保持好** —— 当新证据涓滴而入、旧假设悄悄过时、世界条件在变、你又在十几个相关领域形成新判断 —— 这才是人类放弃 wiki 的原因。维护负担长得比价值快，wiki 死亡。

**LLM 是这个 bookkeeping 的完美匹配**。它不会无聊。不会忘记更新交叉引用。一条新数据来，它可以在一次过程里同时更新 15 个节点。它可以每天早上 8 点自动跑一次 falsifier 扫描而不需要任何提示。**LLM 介入后，维护判断图谱的成本几乎为零**。

**剩下的就是只有人能做的部分**：你决定相信什么、多确信、什么会让你改观；你签下协议；你采取行动。LLM 做剩下所有的事。

这是 "AI as content accelerator"（AI 作为内容加速器）的反面。是 **AI as judgment-engine maintainer**（AI 作为判断引擎维护者）。

## 工作流

### 工作流 A · 新资料进来

1. 你把一篇文章 / 数据点 / 播客笔记放进 Raw
2. 告诉 LLM："摄入这个"
3. LLM 读完，写 Knowledge 摘要页，更新实体页
4. LLM 同时扫描 Cognition Wiki：这条资料触动了任何 active 判断吗？
5. 对每个被触动的判断：在 `evidence:` 末尾追加一行（带时间戳 + 一句话）；评估对应 falsifier 状态；**建议**置信度更新
6. LLM 给你一份简短的 Synthesis 报告："今天这条资料触动了 3 个判断。判断 A：F2 进入'接近触发'。判断 B：证据追加。判断 C：建议置信度 🟡 → 🟢，请确认。"
7. 你确认或否决

### 工作流 B · 每日 falsifier 扫描

1. 每天早晨（计划任务），LLM 扫描所有 active 判断节点
2. 对每个：检查是否有最近的摄入让某个 falsifier 条件向触发靠近了
3. 输出 Daily Synthesis 报告："本周触动 5 个判断，2 个 falsifier 接近触发，1 个演化阶段转换建议，3 个过期判断需要审视"
4. 你花 5 分钟读完。结束。图谱保持活性。

### 工作流 C · 形成一个新判断

1. 读完一篇东西，你有了一个看法
2. 告诉 LLM："给 X 创建一个判断节点。我的观点是 Y。我不确定的地方是 Z。如果出现 W 我就承认错了"
3. LLM 创建节点，初始 `confidence: 🔴`，基于 W 设置 `falsifiers`，链接到相关 Knowledge 页面，登记进 `index.md`
4. 从这一刻起，每次摄入都会自动检查是否触动这个判断

### 工作流 D · 行动后的反馈

1. 你基于某个判断做了某个行动。一段时间后有了结果（对 / 错 / 部分对）
2. 告诉 LLM："把这个反馈摄入到判断 X"
3. LLM 写一份反馈文件：发生了什么、为什么
4. LLM 识别应该更新哪个方法论文件（例如"原协议说做 X，结果表明协议还应该处理 Y"）
5. LLM 更新方法论
6. LLM 反向传播：扫描所有 `methodology` 字段指向这个方法论的判断节点，每个都追加一条 evidence："[日期] 方法论已更新基于反馈 X"
7. 现在每个相关判断都知道方法论演化了。**同一课，只学一次，所有相关判断同时受益。**

### 工作流 E · 周度 Lint

1. 周五下午跑 Lint
2. LLM 扫描两层（Knowledge 层孤立页 / 矛盾，Cognition 层过期判断 / 断证据链 / 接近 falsifier 未承认 / 升格候选）
3. 输出 Lint 报告
4. 你花 30 分钟逐条确认或处理

## 工具 / 最小起步

需要的非常少：
- 一个 markdown 文件目录（Obsidian、Logseq，或者就是一个 `.md` 文件夹）
- 一个能读写文件的 LLM agent（Claude Code、Cowork、Codex、Cursor），配置成会话开始就读 `SCHEMA.md`
- 可选：一个调度任务 / cron / GitHub Action，让"每日 Falsifier 扫描"自动跑

完了。不需要数据库、不需要 embeddings、不需要 vector store、不需要特殊基建。**Wiki 就是代码库**。用 git 做版本历史。

## 与 LLM Wiki 的明确差异

| 维度           | LLM Wiki                    | 认知引擎                                                |
| ------------ | --------------------------- | --------------------------------------------------- |
| **目标层**      | Knowledge（DIKW 第 3 层）       | **Wisdom（DIKW 第 4 层）**                              |
| **产出物**      | wiki 页面 — 实体 / 概念 / 理论 / 综合 | **判断节点** — 带置信度 + 证据链 + 证伪条件                        |
| **架构**       | Raw + Wiki + Schema（3 层）    | Raw + Knowledge + **Cognition** + Methodology（4 层）  |
| **核心操作**     | Ingest / Query / Lint       | + **Falsifier Sweep** + **Feedback Reverse-Update** |
| **LLM 跟踪什么** | 世界上什么是真的 / 资料怎么说            | **你**相信什么 / 多确信 / 什么会让你改观                           |
| **终端验证**     | 无（知识靠内部一致性自洽）               | 行动 → 结果 → 方法论升级 → 所有相关判断同步学习                        |
| **复利对象**     | 知识密度                        | **判断质量**                                            |
| **主体性**      | 隐含（你只是读者）                   | **显式** —— 证伪条件是*你的*，协议是*你的*，反馈是*你的*                 |

**LLM Wiki 是"我想深入学习某个主题"的正确答案。认知引擎是"我需要在某个领域反复做决策、且希望判断在多年里复利"的正确答案**。两者完全可以叠加 —— LLM Wiki 做你的 Knowledge 层底座，认知引擎在它之上加 Cognition + Methodology 两层。

## 引擎 vs 产线

认知引擎是**引擎**。产线是你用它搭出来的东西。

整个架构有三个纵向层：

1. **认知引擎（engine）** —— 通用层：Inbox / Drafts / Memory / Knowledge / Cognition / Methodology（通用部分）。领域无关。本 starter 交付的就是这一层。

2. **Topic（主题）** —— 引擎遇到具体领域的接合点。Topic *不是*"Cognition 在某领域的延伸"那么简单。更准确的公式是：

   ```
   Topic = Σ(该领域的 Cognition 节点)
         × (该领域特化的 Methodology)
   ```

   该领域的 Cognition 节点会逐月积累。Methodology 会随领域特化 —— 投资 Topic 会长出"跳涨暂停建仓协议"；内容 Topic 会长出"卡片蒸馏流水线"。Topic 就是两者的合流点。

3. **产线（Production Line）** —— 完全实例化的 Topic，带每日心跳调度、仪表盘、领域专属协议、和与真实世界结果挂钩的反馈回路（投资的盈亏、内容的互动、产品的指标）。产线是领域完备系统：投资 OS、内容 OS、产品 OS、研究 OS。

starter 只交付第 1 层。第 2、3 层是你自己长出来的。

**为什么这个区分重要。** 大多数从 LLM Wiki 或通用笔记工具过来的读者会默认"OS = 完整 app"。认知引擎更接近一个**通用操作系统** —— 它做的事是运行*你的* Topic。同一台引擎可以同时运行一条投资产线和一条内容产线，共享同一份 Knowledge / Cognition 图谱和同一套反馈纪律。**同一台引擎，不同的 Topic。**

## Starter 包

本仓库包含：
- `cognitive-os.md` —— 本文档（核心思想）
- `SCHEMA.md` —— Schema 定义示例
- `AGENT_PROTOCOL.md` —— Agent 操作协议示例
- `templates/` —— 判断节点 / 仪表盘 / 反馈 / 蒸馏报告 / 巡检报告 的 markdown 模板
- `examples/` —— 不同领域里成熟的判断节点示例（已脱敏）

Starter 包**故意保持最小化**。你应该 fork 它、交给你的 LLM agent、和它一起设计适合你领域的实例化版本。投资、研究、产品、政策、爱好深耕 —— 抽象是一样的，schema 是你自己的。

## 风格说明

本文档**故意保持抽象**。它描述一个范式，不是一个具体实现。具体的目录结构、schema 字段、falsifier 命名、页面格式 —— 都取决于你的领域、你的习惯、你用的 LLM。**正确的用法是把它交给你的 LLM agent，一起协同演化出适合你的实例化**。

如果说 LLM Wiki 是"把'事实是什么'的 bookkeeping 外包"，那么认知引擎就是 **"把'你相信什么、为什么'的 bookkeeping 外包"**。

**你保留的是'相信'这件事本身。你外包的是维护工作。**
